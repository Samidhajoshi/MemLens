About & limitations

What MemLens actually measures, and what it doesn't yet

How it works

MemLens overrides global operator new/operator delete in the C++ file you instrument. Including memlens.h redefines new to capture the file and line of every call site, so each allocation is recorded with its size, location, thread, and timestamp.

When the profiled program exits, MemLens compares every allocation against its matching free: anything never freed is a leak, anything freed twice is a double-free, and anything allocated with new[] but freed with plain delete (or vice versa) is flagged as a mismatch. The engine writes one JSON file; this dashboard is the only thing that renders it.

The health score above is computed from this run's leak count, leaked bytes, and invalid frees — it's a simple weighted heuristic specific to this tool, not an industry benchmark.

Known limitations

  • Only tracks new/delete in the file you instrument — STL, other translation units, and third-party libraries aren't visible unless you also hook malloc/free.roadmap
  • Tracks by pointer address in a single map. A freed address reused later in the same run only shows its most recent allocation in the full list — cumulative statistics stay accurate regardless.
  • No stack traces, just the immediate call site — not the full call chain.
  • A detected double-free skips the second real free() to avoid crashing before the report can be written — the block is deliberately leaked rather than actually double-freed at the OS level.
  • Single snapshot at exit — no timeline sampling and no baseline comparison between runs yet.roadmap
