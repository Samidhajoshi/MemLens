About & Limitations
What MemLens actually does, and what it doesn't

How it works

MemLens overrides global operator new/operator delete in the C++ file you instrument. Including memlens.h redefines new to capture the file and line of every call site, so each allocation is recorded with its size, location, thread, and timestamp.

When the profiled program exits, MemLens compares every allocation against its matching free: anything never freed is a leak, anything freed twice is a double-free, and anything allocated with new[] but freed with plain delete (or vice versa) is flagged as a mismatch. The engine writes one JSON file; this dashboard is the only thing that renders it.

Known limitations

  • Only tracks new/delete in the file you instrument — allocations inside the STL, other translation units, or third-party libraries aren't visible unless you also hook malloc/free (e.g. via LD_PRELOAD).
  • Tracks by pointer address in a single map. If a freed address gets reused later in the same run, the map only reflects that address's most recent allocation — cumulative statistics stay accurate, but the full allocation list is a final snapshot, not a complete history.
  • No stack traces — only the immediate __FILE__/__LINE__ of the call site, not the full call chain.
  • A detected double-free skips the second real free() call to avoid crashing before the report can be written — the block is deliberately leaked rather than actually double-freed at the OS level.
  • Single-process, single-run snapshot — no timeline, no comparison against a previous baseline yet.
