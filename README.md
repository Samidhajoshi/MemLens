# MemLens — C++ Memory Profiler & Leak Detector

MemLens is a lightweight C++ memory-profiling tool that instruments a C++ program, records tracked dynamic-memory allocations, and produces a JSON report that can be explored in a standalone HTML dashboard.

It is designed to help developers spot common memory-management problems without manually inspecting every allocation.

## Features

- **Memory allocation tracking** — records allocation size, source file, line number, timestamp, and thread ID for tracked `new` expressions.
- **Leak detection** — reports tracked allocations that were not deallocated by the end of the run.
- **Invalid-free diagnostics** — detects a repeated deallocation (double free) and mismatches between `new`/`delete` and `new[]`/`delete[]` for tracked pointers.
- **Usage statistics** — reports total allocations and deallocations, current tracked usage, peak tracked usage, leak count, and invalid-free count.
- **Allocation-site summary** — groups tracked allocations by source location.
- **HTML dashboards** — includes a standard dashboard and a dark, IDE-inspired alternative.
- **Thread-safe tracking** — protects shared profiler state with a lock and assigns IDs to observed threads.
- **JSON output** — separates the C++ profiling engine from the browser-based report viewer.

> **Scope note:** MemLens is a course/project-scale profiler, not a replacement for AddressSanitizer, Valgrind, or a production allocator. Its tracking coverage is limited; see [Limitations](#limitations).

## How it works

1. You pass a C++ source file to the `memlens` command-line instrumenter.
2. MemLens prepares an instrumented copy that includes `memlens.h` and adds report-generation calls to `main()`.
3. The instrumented source is compiled with `g++`.
4. The program runs, and the profiler records supported allocations and deallocations.
5. At the end of the run, MemLens writes `memory_report.json`.
6. Open a dashboard and load the generated report to inspect statistics, leaks, allocation sites, and invalid frees.

The profiler uses a header-based allocation hook: including `memlens.h` redirects tracked `new` expressions through the profiler. Global `operator delete` overloads help record deallocation events. A re-entry guard prevents the profiler from recursively tracking its own internal bookkeeping.


## Requirements

- A C++ compiler available as `g++`
- A supported Windows, Linux, or macOS environment
- A terminal opened in the project directory

For Windows, a modern **MSYS2 MinGW-w64** toolchain is recommended. The `g++` executable must be available on `PATH`.

## Build and run

### Windows (PowerShell or Command Prompt)

From the `memlens/` project directory:

```powershell
g++ src/memlens.cpp -o memlens
.\memlens.exe samples\showcase_demo.cpp
```

To run a different example, replace `showcase_demo.cpp` with `clean_demo.cpp`, `leaky_demo.cpp`, `double_free_demo.cpp`, or `mismatch_demo.cpp`.

### Linux

```bash
g++ -std=c++17 -pthread src/memlens.cpp -o memlens
./memlens samples/showcase_demo.cpp
```

### macOS

```bash
g++ -std=c++17 -pthread src/memlens.cpp -o memlens
./memlens samples/showcase_demo.cpp
```

Depending on your setup, `g++` on macOS may refer to Apple Clang. If the build fails, install and use a GCC toolchain compatible with the project.

### Optional: CMake

A `CMakeLists.txt` file is included. The direct `g++` commands above are the straightforward build path; CMake configuration has not been independently verified for every platform.

## View the report

After a successful run, the program writes `memory_report.json` in its working directory.

1. Open `dashboard.html` in a browser.
2. Use the dashboard's **Load report** control to select `memory_report.json`, or drag the report onto the page if supported by the dashboard.
3. To use the alternate theme, open `dashboard-dark-ide.html` and load the same JSON report.

The dashboard may show its bundled sample report when a local file cannot be fetched automatically from a browser opened with `file://`. For reliable results, load the report through the dashboard's file control.

## Understanding the report

The JSON report includes the following information:

| Field | Meaning |
|---|---|
| `totalAllocations` | Number of tracked allocation events |
| `totalDeallocations` | Number of tracked deallocation events |
| `currentMemoryUsage` | Bytes currently attributed to tracked allocations that remain unfreed |
| `peakMemoryUsage` | Highest tracked usage observed during the run |
| `leakCount` | Number of tracked allocations reported as still active at report time |
| `invalidFreeCount` | Number of detected invalid-free events |
| `leaks` | Allocation details for tracked allocations that remain active |
| `invalidFrees` | Details for detected double-free and allocation/deallocation mismatch events |
| `allocationSites` | Allocation counts grouped by source location |

Addresses and thread IDs are useful diagnostic context, but they can vary between runs.

Run these one at a time:

```powershell
.\memlens.exe samples\clean_demo.cpp
.\memlens.exe samples\leaky_demo.cpp
.\memlens.exe samples\double_free_demo.cpp
.\memlens.exe samples\mismatch_demo.cpp
.\memlens.exe samples\showcase_demo.cpp
```

Use the equivalent forward-slash paths on Linux and macOS.

- **`clean_demo.cpp`** demonstrates allocations that are released.
- **`leaky_demo.cpp`** demonstrates allocations that remain active.
- **`double_free_demo.cpp`** demonstrates a repeated delete on a tracked pointer.
- **`mismatch_demo.cpp`** demonstrates allocating with `new[]` and deallocating with `delete`.
- **`showcase_demo.cpp`** combines multiple examples for exploring the dashboard.

These examples intentionally include incorrect memory-management behavior. Run only the supplied demos or source code you trust.

## Limitations

- **Not a complete process-wide memory tracer.** Tracking is centered on `new` expressions in the source file being instrumented. Allocations performed inside STL containers, other translation units, or third-party libraries may not be fully represented.
- **No stack traces.** The report records the immediate source file and line, not a complete call stack.
- **End-of-run reporting.** The current design generates a snapshot rather than a live memory timeline.
- **Pointer-address reuse.** The tracker indexes records by pointer address, so an address reused after deallocation can affect the detailed allocation history for that address.
- **No buffer-overflow detection.** MemLens does not provide guard regions or comprehensive bounds checking.
- **Instrumentation assumptions.** The CLI expects a source file with a `main()` function and uses simple source-text processing to insert report-generation calls. Complex formatting or unusual control flow may require manual instrumentation.
- **Not a security boundary.** Do not use it as a substitute for secure coding practices or established diagnostic tools.

## Troubleshooting

**`File not found`**

Run MemLens from the project directory, and ensure the path you pass is relative to that directory. For example, `samples/leaky_demo.cpp` assumes the `samples/` directory is inside the current working directory.

**`g++` is not recognized**

Install a GCC toolchain and add its `bin` directory to `PATH`. On Windows, MSYS2 MinGW-w64 is a recommended option.

**`memlens.h` cannot be found**

Run the executable from the project root so it can locate the header, or verify that `src/memlens.h` exists. If compiling an instrumented source manually, pass the header directory using `-I`.

**Compilation of the target program fails**

MemLens compiles the instrumented target using C++14. Check the target program's dependencies and language requirements. Programs requiring a newer language standard or extra libraries may need manual compilation adjustments.

**The dashboard displays sample data**

Use **Load report** and select the `memory_report.json` generated by your latest run. A browser opened directly from the filesystem may restrict automatic local-file fetching.

## Future improvements

Potential extensions include broader allocation interception (`malloc`/`free`), stack-trace capture, memory snapshots over time, comparison between runs, and additional diagnostics such as buffer-overflow detection.
